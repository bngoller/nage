# Nage v1 Plan

Status: draft 2, 2026-10-26, amended through milestone 2 (its slices ticked; SPEC decisions 38 to 209). Companion to SPEC.md (draft 3). The spec says what v1 is; this plan says in what order it gets built, what each step proves, and when the household starts using it. Draft 2 folds in two independent reviews: a consistency review of both documents and a skeptical-implementer review of milestones 1 to 3.

## 1. How the plan works

### 1.1 Milestones and slices

- Eight milestones. Each is a coherent feature the household can use after it merges, except milestone 1, which is the skeleton and the pipeline.
- Each milestone is split into vertical slices. A slice goes through every layer it touches: migration, core operation, `nage check` query, route and template, tests, phone layout. A slice is done when its tests pass, the local checks in the README's Commands table are green and it is independently reviewed; once CI (milestone 1 slice 5) and the e2e projects (slice 7) exist, done also means its tests run in CI and its screen passes the phone check that applies to it (1.3, item 3), those gates discharged for the earlier slices when the two slices land (SPEC decision 49), except the busy page's rule 1 check, which waited for milestone 2 slice 6 with the checks of slice 5's sign-in and change-password pages and the home page's own (SPEC decisions 74, 115 and 121).
- Slices within a milestone are ordered so the branch is always runnable: a schema slice precedes the code that queries it, because queries are checked at compile time. A later slice may be cut from a milestone if it runs long; the milestone's usable outcome may not.

### 1.2 Process

- Branch `m<N>-<slug>` from `main`; one PR per milestone; CI green; the maintainer reviews and merges. Nothing merges red. Only the two commits before milestone 1 (SPEC.md and PLAN.md, then a PLAN.md change that requires the fixture guard's deny-list secret only once a fixture exists) landed on `main` without a pull request; since milestone 1, `main` changes only by a fast-forward to a pull request's reviewed head, which marks the pull request merged (SPEC decision 79).
- A regression found after a deploy may land through a `fix/<slug>` PR, tagged `v0.N.x` (SPEC decision 30).
- The PR description has five sections: what landed; how to try it (numbered steps, phone included); SPEC coverage (W, R and INV ids); what was deferred and why; spec amendments, each with its row in SPEC.md section 2.
- Versioning: the PR bumps the workspace version to `0.N.0` (milestone 1's `0.1.0` was set in slice 1, and milestone 2's `0.2.0` came with its slice 9, SPEC decision 190); after the merge the maintainer pushes `v0.N.0`, which runs the release workflow from milestone 2 on (milestone 1's `v0.1.0` runs nothing, SPEC decision 81; a tag pushed by a workflow would not trigger it). The workflow builds the amd64 image `ghcr.io/bngoller/nage:0.N.0` (exact tags only, no `latest`), refuses a tag that is not `v` plus the Cargo version, not annotated or not on `main`, and publishes the image and then the Release page with the packed program, its licence and `SHA256SUMS` (SPEC decisions 166 and 171). From milestone 2 the maintainer no longer redeploys the household server after each tag: 0.2.0 is tried on the laptop, and when the server first gets Nage is the scope session's question (SPEC decision 172).
- Spec changes happen in the same PR as the code that needs them, never silently. A non-goal from SPEC.md section 4 is not built, even when it is easy; the PR template asks.
- Fixed from milestone 1: Rust stable pinned in `rust-toolchain.toml`; sqlx compile-time-checked queries with `.sqlx` committed and `cargo sqlx prepare --check` in CI (the closest thing to a typecheck for SQL); `#![forbid(clippy::float_arithmetic)]` in `nage-core` (INV-3, SPEC decision 39); `cargo deny` with the license check blocking and the advisory check on a schedule (SPEC decision 36); `insta` for goldens; `proptest` for invariants and for parser robustness (no nightly-only fuzzer); Playwright in `e2e/` with two projects (SPEC decision 31), Node a test-time dependency only, pinned with a committed lockfile.

### 1.3 Definition of done, every milestone

1. CI green: fmt, clippy, check, sqlx prepare check, deny licenses, unit, property and golden tests, HTTP tests, `nage check` over every scenario database, migration tests, the fixture guard, the Docker build with container smoke, and the e2e suite.
2. Every SPEC invariant the milestone introduces has the test its SPEC row names; those marked Check also have a `nage check` query and a test that corrupts a database and sees the id reported.
3. Phone checks: the pages SPEC 10.3 names (home, login, setup, categorize queue, register, quick entry, reconcile) pass the full check in the `webkit-phone` project (no page-level horizontal scroll, interactive elements outside running text at least 44×44 CSS px); every other new screen only has no page-level horizontal scroll.
4. After the merge and the deploy, the maintainer follows the PR's "how to try it" steps on the household server (from milestone 2; milestone 2's steps are followed on the maintainer's laptop before the tag, on the final build behind an HTTPS proxy (Caddy with a certificate of its own), from one phone, on a made-up book, and the scripted part again on the published image after the release, SPEC decisions 172, 203 and 204, and later milestones as the scope session decides). A failure there goes through the fix lane.
5. The PR includes a seeded scenario database `fixtures/books/v0.<N>.0.sqlite`, generated by the `xtask seed` command through core operations, for the migration tests of later milestones. Milestone 1's, produced in slice 3, is a freshly migrated database with no book row.

## 3. Milestones

### Milestone 1: skeleton and pipeline

Goal: a repository where every later change is proven by the same pipeline. No feature code.

Usable outcome: `docker compose up` on a laptop serves a placeholder page and `/health`; every CI gate exists and is green.

Slices:

1. [x] **Workspace.** Cargo workspace with `crates/nage-core`, `crates/nage-web`, `crates/nage` (the binary) and `crates/xtask`; `rust-toolchain.toml`; `rustfmt.toml`; workspace lints with clippy warnings denied and the float lint in core; `deny.toml` with the license allowlist; `LICENSE` (AGPL-3.0); `.gitignore`; `.editorconfig`; a README with status, local run and dev setup; the pull request template with the five sections from 1.2.
2. [x] **Binary and server.** `nage --version`; `nage serve` with the configuration defaults of SPEC 5.2 (bind `127.0.0.1:8787`, data directory `./data` created with `backups/`, `NAGE_TZ` validated at start); `nage health` (target derived from the bind address, two-second timeout, exit 0 only on 200, a plain HTTP client without TLS); axum with `/health` (JSON `version` and `ok`; 503 when the database does not answer), `/static/*` embedded with content-hashed URLs (htmx pinned, Pico CSS classless build, `app.css`), and a placeholder `/` on the base layout; the response headers of SPEC 5.3 on every response; graceful shutdown on SIGTERM and SIGINT; `tracing` logs with the hygiene rule of 5.2.
3. [x] **Storage.** Two sqlx pools as in SPEC 5.4: a one-connection writer whose transactions begin with `BEGIN IMMEDIATE`, and a read pool; the PRAGMAs; a 503 "busy" page when the busy timeout is exhausted. Migrations with `0001_init.sql` creating the final `book` table (`CHECK (id = 1)`, minor digits 0 to 3, no trigger), applied by `serve`. One compile-time-checked query so the offline check checks something: `/health` counts the book rows. The sqlx workflow written down in the README: a committed `.env` with `DATABASE_URL=sqlite:target/dev.sqlite` (the dev database) and `SQLX_OFFLINE=true`, so every build is offline and `cargo sqlx prepare` goes live by itself, `cargo build` then `cargo sqlx database setup` to create it, `cargo sqlx prepare --workspace -- --all-targets` after any query change, `SQLX_OFFLINE=true` in the Dockerfile (no CI job sets it: the committed `.env` already makes every build offline, SPEC decision 64), sqlx-cli pinned to the sqlx version, `migrate!("../../migrations")` from the core crate, explicit type overrides on every query (the Money and Date newtypes arrive in milestone 2 slice 1, their sqlx impls with milestone 2 slice 3's first query, SPEC decision 89), the query builder allowed for filters, search and pagination. Timestamps as RFC 3339 UTC written from Rust only. The slice also produces `fixtures/books/v0.1.0.sqlite` through `xtask seed` (section 1.3, item 5) and adds `tempfile` for tests.
4. [x] **Test harness.** A per-test temporary data directory helper on `tempfile` (added in slice 3); the `/health` tests on a migrated (200) and on an unmigrated (503) database, written in slice 3, kept; `insta` with one snapshot (the `/health` body with the version redacted); `proptest` behind nage-core's `test-support` feature with its config (SPEC decision 59), so the first real properties in milestone 2 need no plumbing.
5. [x] **CI.** `ci.yml` with jobs: fmt, clippy, check (all targets), sqlx prepare check (migrates a fresh database first), deny licenses, test, fixture-guard, docker (build the image, start it with an empty volume, run `nage health` inside it), e2e (build the binary, run Playwright). Rust caching; Playwright browsers installed with their dependencies on every run, not cached (SPEC decision 75). A scheduled `advisories.yml` that runs `cargo deny check advisories` and opens an issue on failure. (Slice 5 ships the first six jobs and `advisories.yml`; the docker, e2e and fixture-guard jobs arrive with slices 6, 7 and 8, decision 64.) The release workflow arrives in milestone 2.
6. [x] **Docker.** Multi-stage `Dockerfile`: a Rust builder producing a static `x86_64-unknown-linux-musl` binary with SQLite bundled and the time-zone database embedded; a distroless static runtime; `/data` pre-created and owned by uid 1000; `NAGE_DATA_DIR=/data`, `NAGE_BIND=0.0.0.0:8787`; an exec-form `HEALTHCHECK` calling `nage health`. A local `compose.yaml` for development; and its CI job: build the image, start it with an empty volume, run `nage health` inside it.
7. [x] **Playwright.** `e2e/` with the two projects of SPEC decision 31: `chromium-desktop` (1280×800) and `webkit-phone` (the iPhone 13 profile: a 390×844 screen, a 390×664 viewport). A `webServer` entry per project, each on its own port with its own freshly created temporary data directory, `reuseExistingServer` off; the phone-check helper (page-level scroll width, tap-target size); one smoke test: `/` shows the title, `/health` returns 200; and its CI job: build the binary, run Playwright, the browsers installed with their dependencies on every run (SPEC decision 75).
8. [x] **Fixture intake and guard.** `fixtures/README.md` with the anonymization checklist (section 6), the directory layout and the `expected.json` schema; the guard script and its CI job: it scans every file under `fixtures/` by type, with a layout check (SPEC decision 77), fails on any digit run of seven or more, in a CSV line, a JSON string or key or a book's TEXT value, that is not a date or an amount and does not start with the reserved prefix `999`, and fails on any token from a deny list read from an Actions secret. The secret is required only once `fixtures/csv/` holds a fixture: before that a missing secret is skipped with a notice, so milestones 1 and 2 do not depend on it; after that a missing secret fails the job. A real export never enters the repository: the maintainer anonymizes a copy outside it, and the anonymized fixtures are committed only in milestone 3's PR, once the guard is live (SPEC decision 76).

Out of scope: any table beyond `book`, any form, auth, `nage check`, the pre-migration backup, `nage migrate`, the release workflow.

Verification: the pipeline itself. Done when CI is green on `main`, the Docker job passes, both Playwright projects pass, and `v0.1.0` is tagged.

## 4. Cross-cutting tracks

- **Phone first.** The pages SPEC 10.3 names are built at phone width first and pass the full check in `webkit-phone` within the same slice; every other screen must only avoid page-level horizontal scroll, with wide tables in a scroll wrapper.
- **`nage check` grows every milestone.** A milestone that introduces a Check-marked invariant adds its query, its corruption test and, from milestone 8, its line in the Settings output.
- **Migration fixtures.** Each milestone PR adds its seeded database under `fixtures/books/`, generated by `xtask seed` through core operations and scanned by the fixture guard. From milestone 3 the seed is the household scenario: the starter chart, opening balances, two months of fixture imports, rules, inline recategorizations; later milestones add their own objects (manual entries and tags in 4, transfers in 5, reconciliations in 6, balance updates in 7).
- **Scenario databases.** Integration tests build their books through core operations only, never through raw SQL, so every scenario is also a `nage check` subject.
- **Real-data feedback.** Each deploy is followed by a short note from the maintainer: what broke, what was awkward on the phone, which bank row parsed wrong. A regression goes through the fix lane; everything else becomes the next milestone's first slice.
- **Docs.** `docs/deploy.md` and the README change in the milestone that changes what they describe, never in a catch-up pass.

## 6. Fixture intake and anonymization

Layout: `fixtures/csv/<alias>-<kind>/` (a neutral alias, never the bank's name; SPEC decision 76) with `sample.csv` (the anonymized export), `profile.json` (the profile that parses it), `expected.json` and an optional `rules.json`. `expected.json` is versioned and holds, per selector value (or a single entry for single-account files), the surviving rows as date, amount in minor units, description, payee, memo and bank id, plus the expected outcome counts of a first import; it is written from the parser's output by `cargo xtask fixture-expected` (milestone 3 slice 2) and reviewed in `git diff` (SPEC decision 76; the schema is in `fixtures/README.md`).

Checklist for each export before it enters the repo:

- Keep verbatim: header rows and their spelling, column order, delimiter, quoting, encoding and BOM, line endings, date format, sign conventions, number formatting, trailer or summary lines, blank rows, pending rows if the bank exports them, and a few descriptions with accents, commas and quotes.
- Replace: account numbers, cheque and reference numbers, card digits and bank ids with numbers of the same length that start with `999`; names and e-transfer counterparties with generic ones. Descriptions become generic but keep their shape; an e-transfer line stays an e-transfer line.
- Amounts may be altered; keep signs, magnitudes and any running-balance column arithmetically consistent.
- Include at least: a transfer pair visible from both accounts; two rows with the same amount and date and different descriptions; a refund; a month boundary; for a multi-account export, rows from at least two accounts, and any USD rows the bank emits, which the profile must filter.
- Never commit a real export. The maintainer anonymizes a copy outside the repository and hands over only that (SPEC decision 76); the anonymized fixture is committed in the milestone 3 PR. The guard from milestone 1 fails on long digit runs without the prefix and on the deny list of real tokens kept in an Actions secret, which becomes mandatory with the first committed fixture; it scans the seeded databases too.
