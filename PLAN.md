# Nage v1 Plan

Status: draft 2, 2026-10-26. Companion to SPEC.md (draft 3). The spec says what v1 is; this plan says in what order it gets built, what each step proves, and when the household starts using it. Draft 2 folds in two independent reviews: a consistency review of both documents and a skeptical-implementer review of milestones 1 to 3.

## 1. How the plan works

### 1.1 Milestones and slices

- Eight milestones. Each is a coherent feature the household can use after it merges, except milestone 1, which is the skeleton and the pipeline.
- Each milestone is split into vertical slices. A slice goes through every layer it touches: migration, core operation, `nage check` query, route and template, tests, phone layout. A slice is done when its tests pass, the local checks in the README's Commands table are green and it is independently reviewed; once CI (milestone 1 slice 5) and the e2e projects (slice 7) exist, done also means its tests run in CI and its screen passes the phone check that applies to it (1.3, item 3), those gates discharged for the earlier slices when the two slices land (SPEC decision 49).
- Slices within a milestone are ordered so the branch is always runnable: a schema slice precedes the code that queries it, because queries are checked at compile time. A later slice may be cut from a milestone if it runs long; the milestone's usable outcome may not.

### 1.2 Process

- Branch `m<N>-<slug>` from `main`; one PR per milestone; CI green; the maintainer reviews and merges. Nothing merges red. Only the initial commit (SPEC.md and PLAN.md) lands on `main` directly.
- A regression found after a deploy may land through a `fix/<slug>` PR, tagged `v0.N.x` (SPEC decision 30).
- The PR description has five sections: what landed; how to try it (numbered steps, phone included); SPEC coverage (W, R and INV ids); what was deferred and why; spec amendments, each with its row in SPEC.md section 2.
- Versioning: the PR bumps the workspace version to `0.N.0`; after the merge the maintainer pushes `v0.N.0`, which runs the release workflow (a tag pushed by a workflow would not trigger it). The workflow builds the amd64 image `ghcr.io/bngoller/nage:0.N.0` (exact tags only, no `latest`), attaches the binary, and fails if the tag and the Cargo version differ. From milestone 2 the maintainer redeploys the household server after each tag (section 5).
- Spec changes happen in the same PR as the code that needs them, never silently. A non-goal from SPEC.md section 4 is not built, even when it is easy; the PR template asks.
- Fixed from milestone 1: Rust stable pinned in `rust-toolchain.toml`; sqlx compile-time-checked queries with `.sqlx` committed and `cargo sqlx prepare --check` in CI (the closest thing to a typecheck for SQL); `#![forbid(clippy::float_arithmetic)]` in `nage-core` (INV-3, SPEC decision 39); `cargo deny` with the license check blocking and the advisory check on a schedule (SPEC decision 36); `insta` for goldens; `proptest` for invariants and for parser robustness (no nightly-only fuzzer); Playwright in `e2e/` with two projects (SPEC decision 31), Node a test-time dependency only, pinned with a committed lockfile.

### 1.3 Definition of done, every milestone

1. CI green: fmt, clippy, check, sqlx prepare check, deny licenses, unit, property and golden tests, HTTP tests, `nage check` over every scenario database, migration tests, the fixture guard, the Docker build with container smoke, and the e2e suite.
2. Every SPEC invariant the milestone introduces has the test its SPEC row names; those marked Check also have a `nage check` query and a test that corrupts a database and sees the id reported.
3. Phone checks: the pages SPEC 10.3 names (home, login, setup, categorize queue, register, quick entry, reconcile) pass the full check in the `webkit-phone` project (no page-level horizontal scroll, interactive elements at least 44×44 CSS px); every other new screen only has no page-level horizontal scroll.
4. After the merge and the deploy, the maintainer follows the PR's "how to try it" steps on the household server (from milestone 2). A failure there goes through the fix lane.
5. The PR includes a seeded scenario database `fixtures/books/v0.<N>.0.sqlite`, generated by the `xtask seed` command through core operations, for the migration tests of later milestones. Milestone 1's, produced in slice 3, is a freshly migrated database with no book row.

## 3. Milestones

### Milestone 1: skeleton and pipeline

Goal: a repository where every later change is proven by the same pipeline. No feature code.

Usable outcome: `docker compose up` on a laptop serves a placeholder page and `/health`; every CI gate exists and is green.

Slices:

1. [x] **Workspace.** Cargo workspace with `crates/nage-core`, `crates/nage-web`, `crates/nage` (the binary) and `crates/xtask`; `rust-toolchain.toml`; `rustfmt.toml`; workspace lints with clippy warnings denied and the float lint in core; `deny.toml` with the license allowlist; `LICENSE` (AGPL-3.0); `.gitignore`; `.editorconfig`; a README with status, local run and dev setup; the pull request template with the five sections from 1.2.
2. [x] **Binary and server.** `nage --version`; `nage serve` with the configuration defaults of SPEC 5.2 (bind `127.0.0.1:8787`, data directory `./data` created with `backups/`, `NAGE_TZ` validated at start); `nage health` (target derived from the bind address, two-second timeout, exit 0 only on 200, a plain HTTP client without TLS); axum with `/health` (JSON `version` and `ok`; 503 when the database does not answer), `/static/*` embedded with content-hashed URLs (htmx pinned, Pico CSS classless build, `app.css`), and a placeholder `/` on the base layout; the response headers of SPEC 5.3 on every response; graceful shutdown on SIGTERM and SIGINT; `tracing` logs with the hygiene rule of 5.2.
3. [x] **Storage.** Two sqlx pools as in SPEC 5.4: a one-connection writer whose transactions begin with `BEGIN IMMEDIATE`, and a read pool; the PRAGMAs; a 503 "busy" page when the busy timeout is exhausted. Migrations with `0001_init.sql` creating the final `book` table (`CHECK (id = 1)`, minor digits 0 to 3, no trigger), applied by `serve`. One compile-time-checked query so the offline check checks something: `/health` counts the book rows. The sqlx workflow written down in the README: a committed `.env` with `DATABASE_URL=sqlite:target/dev.sqlite` (the dev database) and `SQLX_OFFLINE=true`, so every build is offline and `cargo sqlx prepare` goes live by itself, `cargo build` then `cargo sqlx database setup` to create it, `cargo sqlx prepare --workspace -- --all-targets` after any query change, `SQLX_OFFLINE=true` in the Dockerfile and every CI job but the prepare check, sqlx-cli pinned to the sqlx version, `migrate!("../../migrations")` from the core crate, explicit type overrides on every query (the Money and Date newtypes arrive in milestone 2 slice 1), the query builder allowed for filters, search and pagination. Timestamps as RFC 3339 UTC written from Rust only. The slice also produces `fixtures/books/v0.1.0.sqlite` through `xtask seed` (section 1.3, item 5) and adds `tempfile` for tests.
4. [x] **Test harness.** A per-test temporary data directory helper on `tempfile` (added in slice 3); the `/health` tests on a migrated (200) and on an unmigrated (503) database, written in slice 3, kept; `insta` with one snapshot (the `/health` body with the version redacted); `proptest` as a dev-dependency with its config, so the first real properties in milestone 2 need no plumbing.
5. [x] **CI.** `ci.yml` with jobs: fmt, clippy, check (all targets), sqlx prepare check (migrates a fresh database first), deny licenses, test, fixture guard, docker (build the image, start it with an empty volume, run `nage health` inside it), e2e (build the binary, run Playwright). Rust caching; Playwright browsers installed with their dependencies and cached. A scheduled `advisories.yml` that runs `cargo deny check advisories` and opens an issue on failure. (Slice 5 ships the first six jobs and `advisories.yml`; the docker, e2e and fixture-guard jobs arrive with slices 6, 7 and 8, decision 64.) The release workflow arrives in milestone 2.
6. [ ] **Docker.** Multi-stage `Dockerfile`: a Rust builder producing a static `x86_64-unknown-linux-musl` binary with SQLite bundled and the time-zone database embedded; a distroless static runtime; `/data` pre-created and owned by uid 1000; `NAGE_DATA_DIR=/data`, `NAGE_BIND=0.0.0.0:8787`; an exec-form `HEALTHCHECK` calling `nage health`. A local `compose.yaml` for development; and its CI job: build the image, start it with an empty volume, run `nage health` inside it.
7. [ ] **Playwright.** `e2e/` with the two projects of SPEC decision 31: `chromium-desktop` (1280×800) and `webkit-phone` (the iPhone 13 profile, 390×844). A `webServer` entry per project, each on its own port with its own freshly created temporary data directory, `reuseExistingServer` off; the phone-check helper (page-level scroll width, tap-target size); one smoke test: `/` shows the title, `/health` returns 200; and its CI job: build the binary, run Playwright, the browsers installed with their dependencies and cached.
8. [ ] **Fixture intake and guard.** `fixtures/README.md` with the anonymization checklist (section 6), the directory layout and the `expected.json` schema; the guard script and its CI job: it scans `fixtures/csv/*.csv` and `fixtures/books/*.sqlite`, fails on any digit run of seven or more that is not a date or an amount and does not start with the reserved prefix `999`, and fails on any token from a deny list read from an Actions secret. The secret is required only once `fixtures/csv/` holds a fixture: before that a missing secret is skipped with a notice, so milestones 1 and 2 do not depend on it; after that a missing secret fails the job. Real exports are handed over privately and committed only in milestone 3's PR, once the guard is live.

Out of scope: any table beyond `book`, any form, auth, `nage check`, the pre-migration backup, `nage migrate`, the release workflow.

Verification: the pipeline itself. Done when CI is green on `main`, the Docker job passes, both Playwright projects pass, and `v0.1.0` is tagged.

### Milestone 2: setup, login, chart of accounts, first deploy

Goal: the ledger core, the chart of accounts and real auth, deployed to the household server with both members signed in.

Usable outcome: from a phone, sign in, build the household's chart of accounts with owners, set provisional opening balances (they are re-dated in milestone 3 when the first imports show the real starting dates), see balances per account with natural signs.

Slices:

1. **Money and dates (core).** `Money` as i64 minor units with the book's minor digits, the small currency table (codes and minor digits only), the display and input formats of SPEC 6.10, checked arithmetic; `Date` and half-open periods on `jiff`; "today" from `NAGE_TZ`. Properties: `parse(format(x)) == x`; overflow refused. The float lint is live. SPEC 6.10, INV-3, INV-5, INV-6.
2. **Schema 0002.** `users`, `sessions`, `accounts` (with `system_key`, `name_folded`, `is_balance_only`, the kind trigger and both unique indexes), `transactions` (origin CHECK with all four values), `postings` (amount CHECK), as in SPEC 7 but without the import, tag and reconciliation columns, which arrive with their milestones. Every foreign key `ON DELETE RESTRICT`; stamps NOT NULL.
3. **Chart of accounts (core).** Roots and system accounts at book creation, found by `system_key`; the starter chart; the naming rules; create, rename (not roots), move within kind with the descendant and depth checks, owner (Assets and Liabilities only), archive (children first, zero balance), unarchive; full-name resolution; balances by account and by kind as of a date. `nage check` is born with INV-1, 2, 4 and 8 to 13, and reports "not initialized" on a database with no book row. Property: random trees never violate INV-8 to 10.
4. **Transactions (core, minimal).** Create a balanced transaction with who/when stamps and version 1; refuse unbalanced sets, fewer than two postings, zero amounts, root accounts and archived accounts. The opening-balance operation (SPEC 6.6, INV-13): Assets and Liabilities only, natural-sign input, nonzero, no default date, create and edit with the version check and 409. This is the only write path for transactions until milestone 3.
5. **Setup and auth (web).** `/setup` with the fields of W1 (password twice, currency select defaulting to CAD, starter chart checkbox), 404 once a user exists; `/login`, `/logout` (POST); argon2id at the SPEC 5.3 parameters in a blocking thread, dummy verification for unknown usernames; sessions with the cookie, sliding expiry and hourly `last_seen_at` rule; the Secure rule from `X-Forwarded-Proto` behind the trust-proxy flag; session middleware on every other route with the 303-and-`next` and `HX-Redirect` conventions; the Origin check against `Host` and `X-Forwarded-Host`; the in-memory lockout returning 429; the body-size limit; self-service password change; `nage init`, `nage user add` (non-admins), `nage user reset-password` with flags and a password prompt or `--password-stdin`. HTTP tests for each rule (INV-27, INV-26).
6. **Base UI.** Layout with navigation and flash messages, Pico CSS plus `app.css`, phone-first navigation; the home page with Assets and Liabilities balances as of today, parents rolled up, joint accounts first then grouped by owner, and the empty state when the starter chart was declined; e2e: a setup project per server that runs `/setup` through the UI and saves the signed-in state, then login and home, on both projects; e2e asserts no CSP console violations with htmx loaded (SPEC decision 40).
7. **Accounts (web).** Tree list, new, edit, archive, unarchive, the opening-balance form with its warning text; every refusal explains itself (W2); the UI says there is no delete.
8. **Migrations and seeds.** The pre-migration backup of SPEC 5.5 (only when migrations are pending, the file name with the last applied migration and the app version, abort on failure, the older-binary message); `nage migrate`; the migration test from `fixtures/books/v0.1.0.sqlite`; `xtask seed` producing `fixtures/books/v0.2.0.sqlite` through core operations (starter chart, a few accounts with owners, opening balances).
9. **Release and deploy.** `release.yml` on `v*` tags with the version check; `deploy/compose.example.yaml` on the household server's service pattern (section 5); `docs/deploy.md` for any Docker host; CI's docker job also runs the e2e setup project against the container. The maintainer deploys `v0.2.0` from the server's runbook vault, adds the second user with `nage user add`, and both members sign in from their phones through `tailscale serve`; the Origin check behind that proxy is verified before the tag is pushed (a mismatch goes through the fix lane).

Out of scope: the register, any import, user admin screens, tags, reports beyond the home balances, the balance-only form field.

Verification: property tests for money and trees; HTTP tests for every auth and lockout rule; `nage check` over the seeded chart; e2e on both projects; the migration test from `v0.1.0`; the container e2e setup. Done when the server runs `v0.2.0`, both members have signed in, `nage check` passes against the live database, and `fixtures/books/v0.2.0.sqlite` is in the repo.

### Milestone 3: import, rules, register, income vs expense

Goal: the must-nail workflow, end to end, on the household's real bank formats.

Usable outcome: for every household account, build a profile once, import the month's export, watch the rows land categorized by rules or in Uncategorized, fix the rest inline in the register, read the income vs expense report for the month. Transfers stay in Uncategorized until milestone 5 (SPEC decision 34), where both legs net to zero.

Prerequisite: anonymized exports from each household bank handed over privately before the milestone starts (section 6), with a note of which accounts each file covers and whether any account is in USD.

Slices:

1. **Schema 0003.** `import_profiles` (with `config_fingerprint_hash`), `imports` (with `selector_value`, `header`, `config_fingerprint_hash`, the date range and `row_count`, no stored outcome counts), `import_rows` (raw as an array, memo, the outcome CHECK with all seven values), `rules` (priority ascending); `postings` gains `import_row_id`, `fingerprint`, `bank_date`, `expects_mirror` and the two partial unique indexes. All foreign keys `ON DELETE RESTRICT`.
2. **Profiles and parsing (core).** The profile config model with a `version` field; the detection rules of W3 step 1 (encoding per file, delimiter, header, skipped leading and trailing lines, header recorded and checked); columns by header name or index; the date patterns, amount modes and number formats of W3 steps 2 and 3; description composition skipping empty cells; skip filters and the selector evaluated on raw cells before parsing; zero-amount rows filtered; ragged rows and duplicate bank ids as parse errors. Build what the fixtures need first; a convention no fixture exercises (headerless files, semicolons, CR/DR suffixes) is cuttable under 1.1 and lands when a fixture needs it. A golden test per fixture directory (`sample.csv` plus `profile.json` gives `expected.json`); property: arbitrary bytes and mutated fixtures never panic. W3.
3. **Import engine (core).** Fingerprint v1 with its fixed test vectors and the normalization rules (INV-17, INV-18); file-hash idempotency (INV-15); step 5a over live postings and over other imports' rows; the rule engine (conditions, operators, signed amounts, case rules, first match wins, `set_payee`, archived targets disabled); transaction creation with the Uncategorized default and the row's memo; rule targets limited to income and expense accounts, so no transfer leg and no `expects_mirror` flag exists before milestone 5; the import record inserted first; dry run as a rolled-back transaction; the import's date range over surviving rows; undo under the SPEC decision 32 rule (in this milestone the only blocking condition that can occur is a later import's duplicate row pointing at the undone postings; the confirmation counts transactions changed since import). Properties: importing twice creates zero; a superset creates exactly the extras; permuting rows keeps the fingerprint multiset; undo then re-import reproduces the original. `nage check` gains INV-15 to 19.
4. **Profile wizard (web).** Upload a sample, detection, the mapping form, number and date options, filters and the selector, a live preview of ten parsed rows via htmx, validation of every row on save with the failing row numbers listed, save; list and edit (name and default account only once the profile has imports; the fingerprint-relevant settings are shown locked). The file input stays in the form and is re-posted for each preview; nothing is stored.
5. **Import run (web).** The form (profile, account picker limited to active non-root Assets and Liabilities, selector value listed from the file and pre-filled from this account's last import with a warning on change, file), the 10 MiB upload limit, 409 on a known hash, 422 with row errors on a parse abort, the preview with counts, date range and the opening-date warning, confirm by re-posting the file with the preview's SHA-256, summary with derived counts; imports list; the undo button with its confirmation page. The row-by-row detail page is the last slice to build and the first to cut.
6. **Rules (web).** List in priority order, create, edit, move up and down, enable, disable, delete, apply rules to uncategorized (bumping versions); targets limited to income and expense accounts. The rules half of W6; the match preview waits for milestone 4.
7. **Register R1 (web).** Per account, newest first, keyset pagination at 100 rows, the true running balance via a window function, bank date when it differs, filters (date range, text over payee, memo and import description, uncategorized only), a parent's own postings only, phone cards; inline category change on a two-posting imported transaction limited to income and expense accounts, with the version check (INV-7) and the imported-leg lock (the first slice of W8); a read-only transaction page. No status column until milestone 6.
8. **Income vs expense R2 (web).** The current month by default with previous and next links (the full period picker arrives in milestone 7), Income and Expenses trees with rollup and "Other" lines, `Expenses:Uncategorized` first with its banner linking to that account's register for the period, the net line, drill-down to postings, empty trees for an empty period. A golden snapshot of the report model.
9. **Fixtures.** The household's exports committed as fixtures with `expected.json` (and `rules.json` where useful) after anonymization per section 6, passing the guard; `xtask seed` extended to the household scenario (starter chart, opening balances, two months of fixture imports, rules, inline recategorizations) for `fixtures/books/v0.3.0.sqlite`.

Out of scope: mirror matching, the review queue, manual-match, the categorize queue with suggestions, rule previews, manual entry, splits, tags, delete and restore beyond undo, any transfer.

Verification: goldens for every fixture; the import and undo properties; HTTP tests for the wizard's refusal, for the hash refusal, for the parse abort, for preview-then-commit with a changed file, and for the version check on the inline change; e2e in `chromium-desktop`: build a profile from a fixture, import it, change one category inline, open R2; e2e in `webkit-phone`: the register and the inline change. Done when a full month for every household account imports on the server with zero parse errors, the report matches a hand count of one account's statement, and `v0.3.0` is deployed.

### Milestone 4: manual entry, editing, categorize queue, tags

Goal: everything a person types by hand, and the fast path for categorizing.

Usable outcome: a cash expense entered from a phone in under 20 seconds; a receipt split across two categories; a wrong import fixed, or deleted and restored; the categorize queue cleared with suggestions and one-click rules; tags on trips and projects.

Slices:

1. **Schema 0004.** `tags`, `transaction_tags` (cascading).
2. **Transactions (core, full).** Create with N postings from the quick-entry shapes (Expense, Income, Transfer) and splits; edit date, payee, memo and counter postings; the opening-balance and balance-update rules of W8; imported-leg immutability (INV-19); soft delete and restore with the archived-account refusal (INV-25); step 5a's `skipped_deleted` path with its test; payee autocomplete; the suggestion query by normalized payee; rule from a transaction with the `normalized payee equals` operator. Properties: random balanced transactions round-trip; unbalanced sets refused; restore returns the pre-delete values. Undo's confirmation now also counts tagged and deleted transactions.
3. **Quick entry and splits (web).** The type switch, payee autocomplete, the split editor with the remaining amount, server-side validation; the transaction edit page; delete, the Deleted view, restore. W7, W8.
4. **Categorize queue (web).** Across accounts, newest first, filters by account and owner; a suggestion per row; accept, pick, split, accept and make a rule, skip; bulk accept for rows sharing a suggestion; the rule match preview; the tag action of rules. The queue half of W6.
5. **Tags (web).** Create inline from forms, the tags page, delete with the count confirmation that also edits rules; filters in R1 and R2. W13.

Out of scope: the review queue, mirror matching, any transfer, reconciliation.

Verification: the properties above; HTTP tests for 422 on unbalanced splits, 409 on stale versions and 422 on editing an imported leg; `nage check` INV-25; e2e in `webkit-phone`: quick entry, a split, three rows categorized, a rule made. Done when a household member clears the queue from a phone without instructions and `v0.4.0` is deployed.

### Milestone 5: transfers and the review queue

Goal: transfers between any two household accounts, in any import order, produce one transaction; the review queue catches what the rules cannot decide.

Usable outcome: the card payment, the savings transfer and a member-to-member e-transfer each show once and never as income or expense; hand-entered rows and near-duplicates are confirmed in one place; the restriction of decision 34 is lifted.

Slices:

1. **Schema 0005.** `review_items` with `import_id`, `created_by` and the full resolution set.
2. **Matching (core).** Mirror match (step 5b) with the four-day window, the tie rule, the reconciled-leaves-bank-date-empty rule and the auto-resolution of open items; manual-match candidates (5c); near-duplicate detection (5d) on transaction dates with the overlapping-range rule; rows held with outcome `review`; resolutions under the final-outcome rule (INV-21), Keep both and Link re-running 5a, stale manual-match candidates; the unmatched-transfer sweep inside the import transaction with the window-containment rule; undo's unlink of matched and linked rows and its reference checks; `nage check` INV-16, 20 and 21. Scenario matrix: both import orders, a rule on neither, one or both sides, offsets of 0 to 5 days, equal and unequal amounts, member-to-member, a manual entry that later imports, a pending row that settles under a new description.
3. **Transfer attach rule and merge (core and web).** The rule of W9 on every path that sets an asset or liability counter (import rule, apply rules, suggestion, inline pick, bulk accept, edit), the confirmation dialog for the interactive paths, the merge with its preconditions and its ordered steps, the flag-clearing rule of W8; rule targets and category pickers opened to Assets and Liabilities.
4. **Review queue (web).** The page from W5 with the three kinds and their actions; counts on the home page and in the import summary.
5. **Pickers.** Transfer pickers list every household account grouped by owner; owner labels throughout.

Out of scope: reconciliation.

Verification: the scenario matrix as integration tests with `nage check` after every step; HTTP 409 on resolving twice; e2e: import two overlapping fixtures in both orders and watch the queue reach zero. Done when a month of the household's real transfers nets out with no duplicate on the server and `v0.5.0` is deployed.

### Milestone 6: reconciliation

Goal: each account proven against its statement, and reconciled postings locked.

Usable outcome: enter a statement date and balance, tick rows until the difference is zero, complete; the register shows what is reconciled; a missed or doubled import shows up as its exact amount.

Slices:

1. **Schema 0006.** `reconciliations` with `completed_hash`; `postings.reconciliation_id`.
2. **Reconciliation (core).** Start (one in progress per account), tick, untick, complete only at zero, abandon (and abandon after reopen returning to completed), reopen the latest completed; the effective date; locks on amount, account, dates and delete (INV-22); auto-untick on edit or delete of a ticked posting; statement equality (INV-23); ordering (INV-24); undo and merge refusing reconciled postings; `nage check` for all three. Property: after each completion the reconciled sum equals the statement balance.
3. **Reconcile page (web).** The candidate list with checkboxes, the live difference via htmx, complete and abandon, reopen on the account page; the status column and lock badges in the register; edit forms respect the locks.

Verification: scenario tests with a seeded account and three statements, plus one deliberately missing and one deliberately doubled posting; HTTP 422 on editing a locked leg and on completing at a nonzero difference; e2e in `webkit-phone`. Done when every household account reconciles to its latest statement on the server and `v0.6.0` is deployed.

### Milestone 7: balance sheet, trends, balance-only accounts

Goal: the rest of the reporting, and the accounts that only have a balance.

Usable outcome: net worth at any date with the identity line; twelve months of category trends with a chart; retirement, house and mortgage balances kept current from statements.

Slices:

1. **Balance-only accounts (core and web).** The flag's field on the account form; the update action in natural sign posting the difference to Valuation Changes (W11, INV-14); the origin flip on edit.

## 4. Cross-cutting tracks

- **Phone first.** The pages SPEC 10.3 names are built at phone width first and pass the full check in `webkit-phone` within the same slice; every other screen must only avoid page-level horizontal scroll, with wide tables in a scroll wrapper.
- **`nage check` grows every milestone.** A milestone that introduces a Check-marked invariant adds its query, its corruption test and, from milestone 8, its line in the Settings output.
- **Migration fixtures.** Each milestone PR adds its seeded database under `fixtures/books/`, generated by `xtask seed` through core operations and scanned by the fixture guard. From milestone 3 the seed is the household scenario: the starter chart, opening balances, two months of fixture imports, rules, inline recategorizations; later milestones add their own objects (manual entries and tags in 4, transfers in 5, reconciliations in 6, balance updates in 7).
- **Scenario databases.** Integration tests build their books through core operations only, never through raw SQL, so every scenario is also a `nage check` subject.
- **Real-data feedback.** Each deploy is followed by a short note from the maintainer: what broke, what was awkward on the phone, which bank row parsed wrong. A regression goes through the fix lane; everything else becomes the next milestone's first slice.
- **Docs.** `docs/deploy.md` and the README change in the milestone that changes what they describe, never in a catch-up pass.

## 5. Deployment on the household server

The repository ships a generic guide and an example Compose file. The host-specific steps (folders, the backup script's database line, the uptime monitor, the health script's count, the tailnet policy, the serve command, the runbook pages) live in the server's own runbook vault and are run by the maintainer from there. Nothing in this repo names an address, a host name or a script path on that machine.

What the repo provides:

- `deploy/compose.example.yaml`: `image` pinned to an exact version, `container_name`, `restart: unless-stopped`, `user: "1000:1000"`, `TZ` and `NAGE_TZ`, `NAGE_DATA_DIR=/data`, `NAGE_BIND=0.0.0.0:8787`, `NAGE_TRUST_PROXY=true`, one published port, the data directory as a long-form bind with `create_host_path: false`, and the image's own health check.
- `docs/deploy.md`: create the data folder owned by uid 1000 before the first start; run `nage init` before publishing the port, or use `/setup` right away; add members with `nage user add`; put `tailscale serve` or any reverse proxy in front for HTTPS on a port of its own, which sets `X-Forwarded-Proto` and `X-Forwarded-Host`; let the host's backup copy the data directory and take a consistent copy of `nage.sqlite` by path, never a bare file copy while the server runs (WAL); redeploy by changing the image tag, pulling, `docker compose up -d`, then `docker compose exec nage nage check`; roll back by restoring the newest `pre-migrate-*` snapshot as `nage.sqlite` with the server stopped and starting the older image; prune `backups/` by hand.

What the maintainer does on the host, following the server's add-a-service checklist: the folders, the Compose project, the start, the backup script's database line, the uptime monitor on `/health`, the health script's container count, the tailnet policy line for the second member, the serve command for HTTPS, and the runbook pages. First done at `v0.2.0`, then an image bump per milestone.

## 6. Fixture intake and anonymization

Layout: `fixtures/csv/<bank>-<kind>/` with `sample.csv` (the anonymized export), `profile.json` (the profile that parses it), `expected.json` and an optional `rules.json`. `expected.json` is versioned and holds, per selector value (or a single entry for single-account files), the surviving rows as date, amount in minor units, description, payee, memo and bank id, plus the expected outcome counts of a first import; it is generated by the parser and reviewed as a snapshot.

Checklist for each export before it enters the repo:

- Keep verbatim: header rows and their spelling, column order, delimiter, quoting, encoding and BOM, line endings, date format, sign conventions, number formatting, trailer or summary lines, blank rows, pending rows if the bank exports them, and a few descriptions with accents, commas and quotes.
- Replace: account numbers, cheque and reference numbers, card digits and bank ids with numbers of the same length that start with `999`; names and e-transfer counterparties with generic ones. Descriptions become generic but keep their shape; an e-transfer line stays an e-transfer line.
- Amounts may be altered; keep signs, magnitudes and any running-balance column arithmetically consistent.
- Include at least: a transfer pair visible from both accounts; two rows with the same amount and date and different descriptions; a refund; a month boundary; for a multi-account export, rows from at least two accounts, and any USD rows the bank emits, which the profile must filter.
- Never commit a real export. Exports are handed over privately; the anonymized fixture is committed in the milestone 3 PR. The guard from milestone 1 fails on long digit runs without the prefix and on the deny list of real tokens kept in an Actions secret, which becomes mandatory with the first committed fixture; it scans the seeded databases too.

## 7. Risks and how the plan handles them

| Risk | Handling |
|------|----------|
| Bank formats stranger than expected (headerless files, summary trailers, multi-account exports, USD columns) | Real fixtures before milestone 3; filters and the selector evaluated before parsing; a golden test per bank; the parser never panics |
| Two members writing at once on SQLite | The single writer connection with `BEGIN IMMEDIATE`, the busy timeout, the 503 page and 409 on stale versions: the single writer and the 503 page from milestone 1 slice 3, the rest from milestone 2 or 3; measured in milestone 8 |
| The Origin check failing behind the proxy on deploy day | The rule compares host and port against `Host` or `X-Forwarded-Host`; verified behind `tailscale serve` before `v0.2.0` is tagged; the fix lane |
| htmx under a strict CSP | Headers and the htmx meta config set in milestone 1 slice 2 (SPEC decision 40); milestone 2 slice 6's e2e run asserts no CSP violations with htmx loaded, before any screen depends on it |
| Safari quirks on phones | WebKit in e2e from milestone 1; the named pages checked at phone width |
| Migrations on real data from milestone 2 | The pre-migration backup, a migration fixture per tag, frozen migration files, the migration suite |
| Transfer legs double-counting before matching exists | Decision 34: no transfer leg can be created until milestone 5 |
| A bad import discovered after categorizing | Undo under decision 32 removes it, counts what is lost, and lets the corrected file in |
| Midnight and time zones | "Today" from `NAGE_TZ` with the bundled time-zone database; tests around date boundaries in milestone 2 |
| A real export leaks into the repo | Private hand-over, the anonymization checklist with the `999` prefix, the guard from milestone 1, review of every fixture change |
| Scope creep | SPEC section 4 is checked in every PR; a non-goal needs a spec amendment first |
| The second household member never adopts it | Both members sign in at milestone 2; that member accepts the categorize queue at milestone 4; the release checklist needs both |
