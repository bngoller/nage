# Nage

Nage is open-source personal accounting for one household. It runs as a single Rust binary on a home server, serves a browser UI that works on a phone, and keeps one set of books in one SQLite file. Under the hood it is a double-entry, cash-basis, single-currency ledger. On the surface it says "paid from Checking to Groceries" and never says "debit" or "credit". The workflow v1 must nail: import bank and card CSV exports, categorize them with rules, and see where the money went.

The specification is [SPEC.md](SPEC.md); the ordered task list is [PLAN.md](PLAN.md).

## Development setup

1. Install [rustup](https://rustup.rs) any way you like. On Arch: `sudo pacman -S --needed rustup cargo-deny`.
2. In the repository, run `rustup toolchain install`. It reads `rust-toolchain.toml` and installs the pinned Rust version with `rustfmt` and `clippy`.
3. Install [cargo-deny](https://github.com/EmbarkStudios/cargo-deny) if your package manager did not: `cargo install cargo-deny --locked`. `deny.toml` is written for cargo-deny 0.20.
4. Install sqlx-cli for the query data check and for changing queries or migrations; see [Database and sqlx](#database-and-sqlx).
5. Install `actionlint` and `shellcheck` (Arch: `sudo pacman -S --needed actionlint shellcheck`) if you edit a workflow or a script under `scripts/`; actionlint lints the workflow files and uses shellcheck on their `run:` scripts.
6. Docker (optional, for the image): `sudo pacman -S --needed docker docker-buildx docker-compose`, `sudo systemctl enable --now docker`, `sudo usermod -aG docker $USER` then a new login, or a reboot when a logout does not refresh the groups (membership of the `docker` group is root-equivalent on the host); the smoke also needs curl, tar, jq and file.
7. Node 26.13.0 for the browser tests: with mise, `e2e/mise.toml` selects it inside `e2e/` (`mise install node` there fetches it); otherwise install it any way you like, npm refuses to install with any other version. Then `cd e2e && npm ci` and `npx playwright install --only-shell chromium webkit` (Chromium's headless shell and WebKit, about 240 MB downloaded, more on disk; `npx playwright install chromium` adds the full Chromium (about 200 MB downloaded, more on disk) for headed runs). On Debian or Ubuntu add `--with-deps` to install the system libraries too. On Arch there is no apt, and Playwright's WebKit builds need flite voice libraries Arch does not package (`extra/flite` ships 7 of the 13; the Ubuntu 24.04 build also needs ICU 74 and libvpx 9, which current Arch no longer ships, and libxml2 2, which it ships only as `extra/libxml2-legacy`), so install Chromium's headless shell only (`npx playwright install --only-shell chromium`) and run the desktop project (`npx playwright test --project chromium-desktop`); the `webkit-phone` project runs in CI on every pull request and on every push to `main`. To run WebKit here anyway, use the container Playwright documents for unsupported distributions, started with `--network host` in place of its `-p 3000:3000` (the test servers bind 127.0.0.1, which Playwright's documented `--add-host=hostmachine:host-gateway` cannot reach): in one terminal `docker run --rm --init --network host --workdir /home/pwuser --user pwuser mcr.microsoft.com/playwright:v1.64.1-noble /bin/sh -c 'npx -y playwright@1.64.1 run-server --port 3000 --host 127.0.0.1'` (an image of about 1 GB; the version must equal the project's Playwright version; `--host 127.0.0.1` because the container shares the laptop's network, where Playwright's own `0.0.0.0` would listen on every interface), then in `e2e/` `PW_TEST_CONNECT_WS_ENDPOINT=ws://127.0.0.1:3000/ npx playwright test`: the browsers run in the container and reach the test servers on this machine through the host network. No check of this repository exercises that recipe. Never run a global `playwright` (on Omarchy `~/.local/bin/playwright` rewrites the mise configuration); `npx playwright` inside `e2e/` is the suite's own.
8. The `sqlite3` command-line tool and jq for the fixture guard (Arch: `sudo pacman -S --needed sqlite jq`; Debian or Ubuntu: `sudo apt install sqlite3 jq`); the guard also needs GNU grep with PCRE, find and iconv, which those systems have.

No Node toolchain is needed to build. Node is a test-time dependency only, for the browser tests in `e2e/` (see [End-to-end tests](#end-to-end-tests)).

## Run locally

Start the server with `cargo run -p nage -- serve` and open <http://127.0.0.1:8787>. In a second terminal, `cargo run -p nage -- health` asks the running server whether it is well: it prints nothing and exits 0 when `/health` answers 200, and prints one line on stderr and exits 1 otherwise. Ctrl-C or SIGTERM stops the server gracefully.

The first start creates `data/nage.sqlite` (with `data/backups/`). Before it listens, `nage serve` applies any pending migrations and logs one `database ready` line with the `path`, the number `applied` and the `schema_version`; a later start applies nothing. While the server runs, SQLite keeps `nage.sqlite-wal` and `nage.sqlite-shm` beside the database; a clean stop removes them. A database written by a newer Nage, or one that cannot be opened, is refused at start with exit 1.

`cargo run -p nage -- check` reads the same database (`--data-dir` or `NAGE_DATA_DIR`, default `./data`) without creating or migrating it and prints one line per invariant violation (`INV-8 ...`, plus `FK ...` for a reference to a missing row), followed by `check: ok (10 invariants)`, `check: not initialized` (a database that has not been set up; exit 0) or `check: N violation(s)` (exit 1); a missing database, or one at another schema version than this binary's, is refused with one line on stderr and exit 1.

Settings come from flags or environment variables, flag over variable over default; an empty variable counts as unset. A bad value is refused at start with a one-line message naming where it came from, and exits 2.

| Variable | Flag | Default | Meaning |
|---|---|---|---|
| `NAGE_DATA_DIR` | `--data-dir` | `./data` | Data directory holding `nage.sqlite`; created with a `backups/` folder if missing |
| `NAGE_BIND` | `--bind` | `127.0.0.1:8787` | IP address and port to listen on; `nage health` reads it too |
| `NAGE_TZ` | `--tz` | the `TZ` variable, then UTC | IANA time zone name |
| `NAGE_LOG` | `--log` | `info` | Log filter, a [tracing filter directive](https://docs.rs/tracing-subscriber/latest/tracing_subscriber/filter/struct.EnvFilter.html) |
| `NO_COLOR` | none | unset | Any non-empty value turns off ANSI colour in the log output (colour is otherwise on when stderr is a terminal); an empty value counts as unset |

`NAGE_LOG` takes a bare level or per-crate directives. For example, `NAGE_LOG=warn,nage_web=debug cargo run -p nage -- serve` logs warnings everywhere and debug detail from the web crate, including the passing `/health` requests that the default level leaves out.

## Docker

Docker is optional. The `Dockerfile` builds an image that holds one statically linked `nage` binary, and `compose.yaml` runs it for development.

Build the image from the repository root with `docker build -t nage:dev .`. It compiles `nage` with `cargo build --release --locked -p nage` inside the official Rust image for Alpine, offline against the committed `.sqlx/` like every other build, and copies the binary into a minimal runtime image that has no shell. The first build compiles everything, about 4 minutes on the maintainer's laptop. Later builds reuse the cache mounts that keep the cargo registry and the build directory between builds, so a rebuild after a small change takes a fraction of that. The cache mounts are shared by every build on the machine, whichever checkout it starts from (a second checkout with older file times could reuse the first one's build output), so build the image from one checkout. The build context is an allow-list in `.dockerignore`: only `Cargo.toml`, `Cargo.lock`, `.cargo/`, `.env`, `.sqlx/`, `crates/` and `migrations/` reach the build, so a new compile-time input outside them is added there.

`docker compose up -d` rebuilds the image first (seconds when nothing changed) and starts the container in the background; open <http://127.0.0.1:8787/>. The port is published on the loopback address only. `docker compose ps` shows `(healthy)` once the image's health check passes, `docker compose logs` prints the server's log (`docker compose logs -f` follows it), and `docker compose down` stops and removes the container. The data lives in the named volume `nage_nage-data`, not in `data/` (the Compose project is named `nage`, so the volume has that name wherever the checkout lives). It survives `docker compose down`; `docker compose down -v` deletes it, and the next start begins with an empty database. `compose.yaml` sets no time zone, so the server runs in UTC. Personal settings, such as a zone or another port, go in a `compose.override.yaml` beside it, which Compose merges by itself and `.gitignore` keeps out of the repository:

```yaml
services:
  nage:
    environment:
      TZ: America/Toronto
    ports: !override
      - "127.0.0.1:18787:8787"
```

`!override` replaces the published port; without it Compose publishes the second port next to the first. The Compose file for running Nage on a server arrives with milestone 2.

`scripts/docker-smoke.sh nage:dev` checks a built image; the CI `docker` job runs the same script. It uses a container and a volume of its own, whose names start with `nage-smoke-`, so it leaves the Compose container and its data alone. It publishes the container on `127.0.0.1:8787`; a second argument picks another port, for example while the Compose container holds 8787: `scripts/docker-smoke.sh nage:dev 18787`. It needs Docker with the compose plugin, curl, tar, jq and file. Each check prints a numbered line naming what it proves, and a passing run ends with the line `docker-smoke: OK, N checks (<image>)`; the first failure names the script line and its exit status, prints the container's log and health log when the container exists, and exits 1. The container, its volume and the scratch directory are removed on every exit, and the image stays. Build the image and run the smoke before committing a change to `Dockerfile`, `.dockerignore`, `compose.yaml` or `scripts/docker-smoke.sh`; after a `Dockerfile` or `.dockerignore` change build with `--no-cache`, since a warm build can reuse what a lost input had already built. The checks, in order:

- The files: the `FROM rust:` tag in the `Dockerfile` equals the `channel` in `rust-toolchain.toml`, and `docker compose config` accepts `compose.yaml`.
- The image: its configuration (user `1000:1000`, `NAGE_DATA_DIR` and `NAGE_BIND`, the exec-form health check on `nage health`, the entrypoint and command, no `VOLUME`, the source label), a statically linked binary compiled by the rustc `rust-toolchain.toml` pins, an empty `/data` owned by 1000:1000 with mode 0700, and `nage --version` running in it.
- The running container: started on an empty named volume with `TZ=America/Toronto`, it turns healthy within 60 s, `nage health` inside it exits 0, `/health` and `/` answer through the published port, and the start-up log names the zone, the bind address, `/data` and every migration applied, with no `/health` request at the default log level.
- Stop and restart: `docker stop` ends the server with exit 0 and its `stopped` line within Docker's 10 s grace period, the volume then holds `nage.sqlite` owned by 1000:1000 with no `-wal` or `-shm` file, and a second start on the same volume applies no migration and turns healthy again.

The image runs `nage` as uid and gid 1000. Its data directory is `/data`, created empty, owned by uid 1000 and with mode 0700: a fresh named volume mounted there takes that owner and mode, while a bind-mounted host directory keeps its own owner and mode and must be writable by uid 1000. The image sets `NAGE_DATA_DIR=/data` and `NAGE_BIND=0.0.0.0:8787` and exposes port 8787; the other variables in the table under [Run locally](#run-locally) work as they do there. Its health check runs `nage health` in exec form (there is no shell) every 30 s with a 5 s timeout, and three failures in a row mark the container unhealthy; until the first success, and for at most the first 30 s, it probes every second and failures do not count; the first success marks the container healthy, and from then on it probes every 30 s. Change the address through `NAGE_BIND` only: `nage health` reads `NAGE_BIND`, so a `serve --bind` override would leave the health check probing the wrong port. The entrypoint is `/usr/local/bin/nage` and the command is `serve`, so arguments after the image name replace the subcommand: `docker run --rm nage:dev --version` prints the version. `nage` runs as the container's PID 1, and `docker stop` sends it SIGTERM, which stops the server gracefully.

`NAGE_TZ` and `TZ` work in the container as they do on the host. Zone names resolve against the runtime image's own time-zone database (Debian's tzdata, part of the base image), never the host's; the copy embedded in the binary is used only in an image without a zoneinfo directory. The image's copy changes when the base image is re-pinned, the embedded one when the `jiff-tzdb` crate is updated in `Cargo.lock`.

Both base images are pinned by digest, as `image:tag@sha256:<digest>` with a comment giving the date the digest was resolved: the builder `rust:1.99.1-alpine3.24` and the runtime `gcr.io/distroless/static-debian13:latest`, where `:latest` only names what was resolved, since distroless publishes no version tags. An update to a base image reaches Nage's image only through a deliberate re-pin, made at each milestone PR together with the action SHAs: `docker buildx imagetools inspect <image:tag>` prints the current index digest, which replaces the old one, and the comment's date changes with it. The Rust tag must equal the `channel` in `rust-toolchain.toml` (the smoke's first check fails otherwise), so a toolchain update changes both files and re-pins the builder's digest for the new tag, since Docker builds from the digest alone and the smoke's first check compares only the tag text (its fourth fails when the binary's compiler is not the pinned one); `rust-toolchain.toml` itself stays out of the build context, because the builder image's own toolchain is the pinned one.

The builder image comes from Docker Hub, which limits anonymous pulls. If a CI run fails on that limit (`toomanyrequests`) and a re-run of the job fails the same way, the `FROM` line switches to `mirror.gcr.io/library/rust:1.99.1-alpine3.24` at the same digest.

## Database and sqlx

Queries are checked against the schema at compile time by [sqlx](https://github.com/transact-rs/sqlx), and the result is committed in `.sqlx/`, so an ordinary build needs no database.

Install sqlx-cli, which provides `cargo sqlx`. Its version must match the sqlx line in `Cargo.toml` (0.9). On Arch: `sudo pacman -S --needed sqlx-cli`. Elsewhere: `cargo install sqlx-cli@0.9.0 --no-default-features --features sqlite --locked`.

The committed `.env` holds `DATABASE_URL=sqlite:target/dev.sqlite` and `SQLX_OFFLINE=true`, and never a secret. Because of the second line every build is offline and reads `.sqlx/`; `cargo sqlx prepare` goes live by itself. A `DATABASE_URL` exported in your shell is never overridden by `.env`. Run every `cargo sqlx` command from the repository root, because the relative database path resolves against the working directory.

- First time: `cargo build`, then `cargo sqlx database setup`. It creates `target/dev.sqlite` and applies the migrations.
- After a migration change: `cargo sqlx migrate run`. A released migration is never edited; an edit to an unreleased one changes its checksum, so use `cargo sqlx database reset -y` and delete `data/` instead.
- After a query change: `cargo sqlx prepare --workspace -- --all-targets`, then commit the changes in `.sqlx/`. Every query carries explicit type overrides for computed columns, booleans, dates and money (`"count!: i64"`), and the query builder is used only for filters, search and pagination. The migrations are embedded by `sqlx::migrate!("../../migrations")` in nage-core, whose `build.rs` reruns the build when a migration file changes.
- Before every commit: `cargo sqlx prepare --check --workspace -- --all-targets`. `cargo clean` deletes `target/dev.sqlite`, so re-run `cargo sqlx database setup` before the check.

The Arch `sqlx-cli` links the system SQLite (3.54), while the Nage binary bundles 3.51.3 and the tests run the migrations through the bundled library. A migration that needs a newer SQLite than 3.51 passes `cargo sqlx migrate run` and fails the tests.

CI sets no `SQLX_OFFLINE`: the committed `.env` makes every job offline, and the prepare-check job goes live by itself after installing sqlx-cli with that command (bundled SQLite 3.51.3, the same as the binary) and migrating a fresh `target/dev.sqlite`.

`fixtures/books/v0.1.0.sqlite` is a freshly migrated database with no book row. Tests open a copy of it, never the file itself. It is frozen with `0001_init.sql` once `v0.1.0` is tagged; the next book and its regeneration arrive with milestone 2 slice 8. `fixtures/README.md` describes the fixture layout, the anonymization checklist, the hand-over of exports and the guard (see [Fixtures](#fixtures)).

## Currency table

`crates/nage-core/src/currency/table.rs` lists every current ISO 4217 currency with 0 to 3 minor digits, codes and digits only, for the setup page's currency select; a book keeps the digits of the currency it was set up with. `cargo xtask currencies` writes the file from ISO 4217 list one, the XML file SIX Group publishes, and the file names the list's publication date. To refresh it after an ISO amendment, download the list outside the repository with `curl -fsSL -o /tmp/list-one.xml https://www.six-group.com/dam/download/financial-information/data-center/iso-currrency/lists/list-one.xml` (SIX spells the path `iso-currrency`), run `cargo xtask currencies --from /tmp/list-one.xml --out crates/nage-core/src/currency/table.rs`, update the publication date and the counts and code lists that `crates/nage-core/src/currency/tests.rs` pins, and review the diff before you commit it. The command never downloads anything and refuses a list it cannot read without touching the table.

## Fixtures

`fixtures/` holds the test fixtures: one seeded book per released version under `books/`, and anonymized bank exports under `csv/<alias>-<kind>/`, each directory with a `sample.csv`, a `profile.json`, an `expected.json` and an optional `rules.json`. The alias is a neutral word that is not derived from the bank's name, so no file, path or book in the repository names a bank. `fixtures/README.md` is the record: the layout, the anonymization checklist, the hand-over of a real export, the `expected.json` schema and the guard's known limits. A real export never enters the working tree, a branch or a Claude Code session, because the history is public and permanent. The maintainer anonymizes a copy outside the repository, checks it with the guard and only then copies it in; the first exports arrive in milestone 3.

`scripts/fixture-guard.sh` is the guard, and `scripts/fixture-guard-selftest.sh` proves the guard's rules that its checks name, on synthetic fixtures that it builds in a temporary directory (14 checks, each naming what it proves). Run the self-test first, then the guard, which reads the deny list from the environment variable `FIXTURE_DENY_LIST`:

```
scripts/fixture-guard-selftest.sh
FIXTURE_DENY_LIST="$(cat ~/.config/nage/fixture-deny-list)" scripts/fixture-guard.sh
```

Without an argument the guard scans the repository's `fixtures/` with the layout check on; today that is `fixtures/README.md` and the committed book, and a clean run ends with `fixture-guard: OK, 2 file(s) scanned`. Given paths instead, it scans those files or directories with the layout check off, which is how a candidate export is checked before it is copied in (`scripts/fixture-guard.sh /path/to/candidate.csv`): a file that is neither `.json` nor `.sqlite` is read as a CSV whatever its name, and the deny list is required there. `scripts/fixture-guard.sh --help` prints the usage. The guard needs the tools of item 8 of [Development setup](#development-setup).

The guard fails on:

- a path under `fixtures/` outside the layout (a stray file, a `-wal` side file, a directory name with an uppercase letter or no hyphen), and a `csv/` directory missing its `sample.csv`, `profile.json` or `expected.json`;
- a CSV with a UTF-16 byte-order mark or a NUL byte, or that is neither valid UTF-8 nor decodable as Windows-1252, or with a run of seven or more digits that does not start with `999`, is not an eight-digit date from 19000101 to 20991231, and is not the integer part of an amount written with a period and one to three decimals (`1234567.89`); a decimal comma is never exempt;
- a JSON file that jq cannot parse (an empty file passes), or whose string values or keys hold such a digit run (JSON numbers go through the deny list alone);
- a seeded book that cannot be opened or holds no table, or whose TEXT values hold such a digit run (the guard opens a copy read-only, never the committed file; integers and BLOBs are not scanned, a value of 32 or more hexadecimal characters and a password hash are exempt, and a TEXT value holding a NUL byte fails);
- an entry of the deny list, in any file or in any path name under `fixtures/`.

A number written in groups split by any non-digit (spaces, hyphens, periods, slashes), and anything shorter than seven digits, escape the digit rule; they are the deny list's job. `fixtures/README.md` states this and the other limits of the guard.

The deny list is one entry per line, trimmed; blank lines and lines starting with `#` are ignored, an entry shorter than two characters is an error, and a list that holds no entry at all counts as missing. Entries are matched as fixed strings, whole words, in any letter case (`example.com` matches inside `a@example.com`, `cedar` does not match `cedarwood`); an entry made only of digits matches at digit boundaries wherever it stands. It holds the real account, card, cheque and reference numbers, the bank's names and domains and the names of its products, account packages and programmes, and the household members' and counterparties' names, addresses and mailbox addresses, spelled as the exports spell them, accents included. The list lives in two places and nowhere else: the maintainer's private file outside the repository, `~/.config/nage/fixture-deny-list` (mode 0600), for local runs, and the repository secret `FIXTURE_DENY_LIST` for CI, created with `gh secret set FIXTURE_DENY_LIST < ~/.config/nage/fixture-deny-list` before milestone 3's pull request. While `fixtures/csv/` holds no file, a missing list only skips the deny-list scan: the guard prints a notice and the digit and layout checks still run. Once `fixtures/csv/` holds a file, a missing list fails the run. A pull request from a fork gets no secret, so it fails the job once fixtures exist.

A failure reads `fixture-guard: FAIL <place>: <hint>`. The main places are `<file>:<line>` for a CSV or text line, `<file>: JSON string N` or `<file>: JSON number N` for JSON (string N counts the string values in document order, then the keys, each object's in sorted order; number N counts the numbers in document order), and `<file>: <table>.<column> (value N)` for a book (the Nth TEXT value read); a problem with a whole file names the file alone, and a layout problem the path. A digit run is reported with its length and first three digits, and a deny-list hit as `deny-list entry K`, where K is the entry's line number in your list (comments and blank lines count). Nothing that matched is printed, neither an entry nor a run nor a cell, because the run log is public; a path that matches an entry is the one thing that is necessarily named. Under GitHub Actions each problem is also an `::error` annotation in the run.

The exit code is 0 when nothing was found, 1 when something was (a missing list with a fixture present, or a path argument that does not exist, included), and 2 for a usage error, a missing tool or a grep without PCRE, a `--fixtures-dir` that is not a directory, a temporary directory the guard cannot create, a CSV, a book or (with a list) a text file the guard cannot read (an unreadable JSON file is reported as not valid JSON), or a deny-list entry shorter than two characters.

Run the self-test and the guard, with your deny list, before a commit that changes anything under `fixtures/` or either guard script, and run the guard with the list again before a push whose commits touch `fixtures/`: CI runs after the push, when the file is already public, so the local run is the real gate. The CI job is described under [Continuous integration](#continuous-integration).

## Tests

Each crate keeps its integration tests in `crates/<crate>/tests/`, with helpers local to that crate in `tests/common/` where it needs them. Helpers shared by all crates (temporary directories, opening a fresh or migrated database, copying the committed fixture, the proptest configuration) live in `nage_core::test_support`, behind the `test-support` cargo feature that only dev-dependencies enable, so a production build never carries them.

- Goldens use [insta](https://insta.rs), except each CSV fixture's expected parse, which from milestone 3 on is the fixture directory's `expected.json` (see [Fixtures](#fixtures)). Snapshots are files under `snapshots/` beside the test, and the `.snap` files are committed. To write or refresh one, run `INSTA_UPDATE=always cargo test -p <crate> --test <target>` (the test file's stem; `--lib`, or `--bin <name>` in a binary crate, for a snapshot under `src/`) and read the result in `git diff` (a new snapshot is untracked: read the file itself, or run `git add -N <file>` first). [cargo-insta](https://crates.io/crates/cargo-insta) is optional and only needed for `cargo insta review` (Arch: `sudo pacman -S --needed cargo-insta`). Under `CI=true` a missing or stale snapshot fails and nothing is written.
- Properties use [proptest](https://proptest-rs.github.io/proptest/). Each runs 256 cases by default; `PROPTEST_CASES=4096 cargo test -p nage-core` runs more, and `PROPTEST_RNG_SEED` reproduces a run. A failing case is saved under `crates/<crate>/proptest-regressions/` and replayed first on every run; commit those files. CI runs 1024 cases; a failure there prints a `cc <seed>` line to add to the crate's regression file.
- A test that panics while it still holds its temporary directory keeps it, named `nage-test-*` under the system temp directory, for inspection (a directory dropped before the failing assertion is removed). `rm -rf /tmp/nage-test-*` clears them.

### End-to-end tests

The browser tests live in `e2e/`, the only Node in the repository. It is an npm project: `package.json` and its lock file `package-lock.json` (committed; `npm ci` installs exactly what the lock file holds, and `npm install` is run only to change a dependency), `.npmrc`, `mise.toml` (the Node version), `tsconfig.json`, `playwright.config.ts`, `serve.mjs` (starts one Nage server per project), `lib/phone.ts` (the phone check), `tests/` (the specs; `tests/phone/` holds the phone checks of the named pages) and `scripts/check-licenses.mjs`. The tests, the configuration and the helper are TypeScript. Every test's doc comment ends with a `Proves:` line, as the Rust tests' do. Set up Node and the browsers as described in item 7 of [Development setup](#development-setup), run the `npm` and `npx` commands from inside `e2e/` (the licence check, `node e2e/scripts/check-licenses.mjs`, runs from the repository root), and never use a global `playwright` command: `npx playwright` is the suite's own.

To run the suite, build the binary it starts with `cargo build -p nage`, then `cd e2e && npx playwright test`. `npx playwright test --project chromium-desktop` runs one project (the only one that runs natively on current Arch Linux, see below), and `npx playwright test --list` lists the tests without running them. The suite starts the binary at `target/debug/nage` and never builds it, so run `cargo build -p nage` right before the suite (the suite reads `target/debug/nage`, cargo's default location; a `CARGO_TARGET_DIR` or `build.target-dir` setting puts the binary elsewhere): that file is stale after an edit to anything it is built from, and after `cargo test --workspace` it is the test build, with nage-core's `test-support` feature on; `serve.mjs` stops with a message and exit code 2 when that file is missing.

There are two projects. `chromium-desktop` runs Chromium's headless shell at 1280×800 against a server on `127.0.0.1:8791`. `webkit-phone` runs WebKit with Playwright's iPhone 13 profile (a 390×844 screen, a 390×664 browser viewport, device scale factor 3, mobile and touch emulation) against a server on `127.0.0.1:8792`. Playwright starts both servers on every run, whichever project you select, so both ports must be free; a stale server on either port fails the run at once with Playwright's "is already used" message instead of being tested. `serve.mjs` creates a fresh directory named `nage-e2e-*` under the system temporary directory, runs `nage serve --bind 127.0.0.1:<port> --data-dir <that directory> --tz UTC`, and on SIGTERM (which Playwright sends at the end of the run) waits for Nage to stop cleanly, removes the directory and exits with Nage's status, so every run starts from an empty database and leaves nothing behind whenever Playwright ends the run itself (a pass, a failure, Ctrl-C or its global timeout). If Playwright is killed instead (for example by the `timeout` command, or when its terminal closes), it never sends that SIGTERM: both servers keep running in their own sessions and keep their directories, and the next run fails at once with "is already used"; `pkill -TERM -f 'node serve.mjs 879[12]'` stops them, and each launcher then removes its directory. The log level follows `NAGE_LOG` as usual. `retries` is 0, because a flaky test is a bug to fix, and `bypassCSP` is never set, so every test that loads a Nage page runs under the real security headers (the phone-check self-test's synthetic pages carry none). `tests/smoke.spec.ts` runs in both projects: `/` answers 200 with the title `Nage`, and `/health` answers 200.

The phone check is the executable form of the phone-layout rules of SPEC 10.3. `lib/phone.ts` implements it once, and a spec under `tests/phone/` applies it to a page in the `webkit-phone` project; the home page is the first. Rule 1 applies to every screen: the page must not scroll sideways, meaning the document is no wider than the window, and the window is no wider than the phone's 390 CSS pixels (a page without the `width=device-width` viewport tag renders at 980 and fails). Rule 2 applies to the named pages (home, login, setup, the categorize queue, register, quick entry and reconcile): every rendered interactive element (link, button, form control, summary, or anything with a button or link role or a `tabindex` other than -1) measures at least 44×44 CSS pixels. A link inside a sentence is exempt, as in WCAG 2.5.5: a link laid out as inline text, within a block of text that has a rendered letter or digit of its own outside any interactive element (neither text in a nested block, such as a heading or an inline-block label, nor hidden text counts). The exemption is narrow and applies to links only. A link alone in its block, a link beside a heading, a link beside an inline-block label, a link beside hidden text, links separated only by spaces or punctuation, an inline-block link, a button and a form control (a labelled checkbox included, whatever its styling) are all targets and must measure 44×44. A failure lists every offender with its tag, id, text and size. `tests/phone-check.spec.ts` is the helper's own test on synthetic pages, in both projects: it proves that a conforming page passes, that each rule fails on a page that breaks it, alone and through the full check, that a small standalone control is named with its size and that a control short on one side only is an offender while a 44×44 one is not, that every kind of interactive element is measured and each exclusion is not, that the exemption holds for a link in a sentence (beside letters or beside digits alone, or inside an inline-block label with its own text) and not for the other cases it tests (a link alone in its block, links separated only by a space or by a middle dot, a link beside a heading, a link beside an inline-block label, a link whose text sits in a nested element, an inline-block link in a sentence, a button or checkbox laid out inline in a sentence, a labelled checkbox, a link beside hidden or zero-size text), and that unrendered elements are skipped. The home page has no interactive element yet, so rule 2 is proven by that self-test until a screen gives it something to measure.

When a test fails, the `list` output names the test and the assertion. Playwright keeps a trace of each failed test under `e2e/test-results/` (ignored by git), and a screenshot when the test had a page open (the `/health` smoke uses the request fixture alone, so it gets none); open a trace with `npx playwright show-trace test-results/<test>/trace.zip` (the viewer needs a headed Chromium-based browser: the full Chromium of the optional install in item 7, or a system Chrome or Edge). In CI the failed job uploads `e2e/test-results/` as the artefact `e2e-failure-<attempt>`, kept for 7 days (see [Continuous integration](#continuous-integration)).

Two more checks belong to the suite, since Playwright runs TypeScript without checking it and the Node dependencies are licence-gated like the Rust ones. `npx tsc --noEmit` in `e2e/` typechecks the tests, the configuration and the helper. `node e2e/scripts/check-licenses.mjs` (it needs no installed packages) reads the `license` of every package in the lock file and fails on a licence outside its allowlist (Apache-2.0 and MIT, one line per licence naming the packages that need it), on a package with no licence, and on any package that declares an install script. A new dependency or a new licence is the maintainer's decision.

On current Arch Linux the `webkit-phone` project cannot run natively, because Playwright's WebKit builds need libraries Arch does not package. There the desktop project runs locally and `webkit-phone` runs in CI on every pull request and push to `main`; item 7 of [Development setup](#development-setup) has the reasons and the commands for running WebKit locally anyway, Playwright's documented container recipe adapted to host networking: `run-server` inside `mcr.microsoft.com/playwright:v1.64.1-noble` started with `--network host` (Playwright's documentation publishes the port with `-p 3000:3000` instead), then `PW_TEST_CONNECT_WS_ENDPOINT=ws://127.0.0.1:3000/ npx playwright test`, so that the browsers run in the container and reach the test servers through the host network. That recipe is optional and no check of this repository exercises it. The desktop project takes about 5 seconds on the maintainer's laptop.

## Continuous integration

`.github/workflows/ci.yml` runs on every pull request, on every push to `main` and, once the file is on `main`, by hand from the Actions tab. It has one job per check in the Commands table above: `fmt`, `clippy`, `check (all targets)`, `sqlx prepare check`, `deny licenses` and `test`, plus the `docker`, `e2e` and `fixture-guard` jobs. Each of the six runs the table's command with `--locked` added where cargo accepts it. The six run on an explicitly named runner image (`ubuntu-24.04`), install the Rust version that `rust-toolchain.toml` pins, and the four that compile (clippy, check, sqlx and test) cache their builds per job. Every action is pinned to a full commit SHA with a `# vX.Y.Z` comment naming the release, and the pins are re-resolved at each milestone PR; GitHub's repository setting that requires actions pinned to a full commit SHA is on, so a workflow using an unpinned action fails at once. `main` is protected by a ruleset: it moves only to a commit on which the nine CI checks have passed (the advisory check is not among them), and it can be neither force-pushed nor deleted. No pull request is merged with GitHub's merge button or API, since in a test the merge commits GitHub made carried the maintainer's local offset whatever zone the request sent (SPEC decision 79): the maintainer fast-forwards `main` to the pull request's reviewed head with `git push origin <head>:main`, which marks the pull request merged, so `main` holds only commits made under UTC. A branch whose base moved is brought up to date locally with `TZ=UTC git merge --no-edit origin/main`, never on GitHub (the ruleset does not require an up-to-date branch and the repository's "Always suggest updating pull request branches" setting is off, so GitHub offers no Update branch button).

The `docker` job runs on the same runner image with no Rust toolchain or cache step. It lints the smoke script with `shellcheck`, builds the image with the runner's own Docker (`docker build --tag nage:ci .`) and runs `scripts/docker-smoke.sh nage:ci`, the smoke described under [Docker](#docker). The build is cold on every run, because cache mounts are never exported and every run gets a fresh runner: about 4 minutes on the maintainer's laptop, and the runner's time is recorded in the milestone PR. The job never pushes the image. To reproduce it locally, run `shellcheck scripts/docker-smoke.sh`, then `docker build -t nage:dev .` and `scripts/docker-smoke.sh nage:dev`. A local pass does not guarantee a CI pass. Your build reuses the cache mounts while the job's starts with empty ones, and cargo does not track sqlx's offline data in `.sqlx/` (the query macros read it while compiling), so a build context that has lost `.sqlx/` still builds locally from the cached `nage-core` and fails in the job. `docker build --no-cache -t nage:dev .` compiles everything, as the job does, because on Docker 29 `--no-cache` skips the layer cache and starts the cache mounts empty (later builds start from what it leaves). The runner's Docker and `shellcheck` can also be older than yours. For one, the runner's BuildKit does not apply `COPY --chmod` to a destination directory that `COPY` creates itself (it stays 0755, where a newer BuildKit applies the mode), which is why the `Dockerfile` copies `/rootfs/`, whose `data` subdirectory keeps its 0700, rather than using `--chmod` on `/data`.

The `e2e` job runs on the same runner image, has no `needs` and a 30-minute timeout, and installs the pinned Rust toolchain and restores the cargo cache as the clippy, check, sqlx and test jobs do. Its steps, in order: `cargo build --locked -p nage` builds the debug binary the suite starts; `actions/setup-node` installs the Node version that `e2e/mise.toml` pins (the runner has no Node 26, so it is downloaded on every run); `node e2e/scripts/check-licenses.mjs` checks the lock file's licences before the Node packages are installed; `npm ci` installs the packages; `npx tsc --noEmit` typechecks the suite; `npx playwright install --with-deps --only-shell chromium webkit` installs Chromium's headless shell, WebKit and their system packages through apt; and `npx playwright test` runs both projects with a single worker. The browsers, about 240 MB, are downloaded on every run and are not cached, because Playwright's documentation advises against caching them: restoring the cache takes about as long as the download, and the system packages cannot be cached at all. When the job fails, a last step uploads `e2e/test-results/` (traces and screenshots) as the artefact `e2e-failure-<run attempt>`, kept for 7 days; a WebKit-only failure may not reproduce on a machine without WebKit, so the evidence travels with the run. A failed test appears as an annotation on the pull request through Playwright's `github` reporter, and a type error appears as one too, through the tsc problem matcher that `actions/setup-node` registers, but without its file (tsc runs in `e2e/` and prints paths relative to it, while the runner resolves the matcher's paths against the repository root and drops a path that does not exist there), so the typecheck step's log is where the file and line are. The job's duration is recorded in the milestone PR. To reproduce it locally, run `cargo build --locked -p nage` and `node e2e/scripts/check-licenses.mjs`, then in `e2e/` `npm ci`, `npx tsc --noEmit` and `CI=true npx playwright test` (`CI` selects the single worker, the `github` reporter and the ban on `test.only`; on Arch add `--project chromium-desktop`; see [End-to-end tests](#end-to-end-tests)).

The `fixture-guard` job runs on the same runner image, has no `needs`, no Rust toolchain or cache step and a 10-minute timeout. It lints both guard scripts with `shellcheck`, runs `scripts/fixture-guard-selftest.sh` (14 checks on synthetic fixtures) and then `scripts/fixture-guard.sh`, with the repository secret `FIXTURE_DENY_LIST` passed to that step alone as the environment variable of the same name. The secret does not exist yet, so while `fixtures/csv/` holds no file the guard prints a notice that the deny-list scan was skipped (also an annotation in the run's summary) and passes; the digit and layout checks still run. Once a fixture is committed, a missing secret fails the job, as does a pull request from a fork, which receives no secret. The log names places and hints, never a matched entry, run or cell (a path name that holds an entry is necessarily named), and the job uploads no artefact, since that would republish fixture data. The job's duration is recorded in the milestone PR. To reproduce it locally, run `shellcheck scripts/fixture-guard.sh scripts/fixture-guard-selftest.sh`, `scripts/fixture-guard-selftest.sh` and `scripts/fixture-guard.sh` (with `FIXTURE_DENY_LIST` set from the private list once the secret exists; see [Fixtures](#fixtures)).

To read a failed job, open the run from the pull request's Checks tab and expand the red step. For a failed `e2e` job, the pull request also shows the failed tests as annotations, and any type error as one without its file (the typecheck step's log has the file and line); the step's log holds the `list` output; and, when at least one test ran (a failure before the suite starts uploads nothing), the run's summary page lists the `e2e-failure-<run attempt>` artefact, a zip of `e2e/test-results/` whose `trace.zip` files open with `npx playwright show-trace`. To reproduce the test job locally, run `CI=true INSTA_UPDATE=no PROPTEST_CASES=1024 cargo test --workspace --locked`; for the other five jobs, run the table's command with `--locked` added where cargo accepts it, as `ci.yml` does (without it, a lock file that does not match the manifests passes locally and is rewritten). The sqlx prepare check job first migrates a fresh dev database, so reproduce it from one: `mkdir -p target`, `rm -f target/dev.sqlite target/dev.sqlite-wal target/dev.sqlite-shm` and `cargo sqlx database setup`, then the check; against an older dev database the check can pass where the job fails. The job's sqlx-cli is the `cargo install` build from Database and sqlx (bundled SQLite 3.51.3), not the Arch package.

`.github/workflows/advisories.yml` runs `cargo deny --locked check advisories` every Monday at 06:23 UTC and by hand, and on pull requests that change `advisories.yml`, `deny.toml` or `Cargo.lock`; the schedule and the manual button work once the file is on `main`. It is never a required check. When a scheduled or manual run fails it opens one issue titled "cargo deny check advisories failed", or comments on that issue while it is open. The `ignore` list in the `[advisories]` table of `deny.toml` holds every advisory the project has accepted, each with its id, a reason and when to revisit it; adding an entry is the maintainer's decision. GitHub pauses scheduled workflows in a public repository after 60 days without activity; re-enable it with `gh workflow enable advisories.yml`.

Run `actionlint` before committing a workflow change and `shellcheck scripts/*.sh` before committing a script change. Run `scripts/fixture-guard-selftest.sh` and `scripts/fixture-guard.sh` before committing a change under `fixtures/` or to either guard script, and the guard with your deny list before pushing commits that touch `fixtures/`.
